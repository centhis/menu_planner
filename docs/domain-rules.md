# Правила предметной области и работы со свободным текстом

**Версия:** 0.2  
**Назначение:** определить, какие решения принимает модель, какие принимает программный код и как пользовательский текст превращается в безопасные прикладные операции

## 1. Основной принцип

Система сочетает вероятностную интерпретацию и генерацию с детерминированной прикладной логикой.

Модель используется для:

- понимания естественного языка;
- классификации намерения;
- извлечения параметров;
- создания вариантов меню и рецептов;
- объяснений;
- исправления черновиков по машинным ошибкам.

Код используется для:

- управления состоянием;
- разрешения операций;
- проверки бизнес-правил;
- арифметики;
- изменения базы;
- версионирования;
- commit и rollback;
- аудита.

Правило:

> Ни пользовательский текст, ни вывод модели не изменяют подтверждённые данные напрямую.

## 2. Уровни данных

### 2.1. Подтверждённые данные

Источник истины:

- профиль;
- строгие ограничения;
- активное меню;
- версии меню;
- рецепты;
- каталог магазина;
- список покупок;
- статусы покупок;
- подтверждённые сопоставления продуктов.

### 2.2. Черновики

Результаты модели до commit.

Минимальные статусы:

```text
created
generated
validation_failed
revision_requested
validated
waiting_confirmation
committed
rejected
abandoned
```

### 2.3. Разговорный контекст

Может содержать:

- стиль общения;
- недавние пожелания;
- пояснения;
- временные детали.

Не является единственным источником строгих ограничений или активного состояния.

## 3. Модель обработки свободного текста

Каждое пользовательское сообщение проходит через слой интерпретации.

Результат интерпретации должен быть структурирован:

```json
{
  "intent": "replace_meal",
  "confidence": 0.93,
  "parameters": {
    "date": "YYYY-MM-DD",
    "meal_type": "dinner",
    "requirements": {
      "max_active_time_minutes": 20,
      "exclude_equipment": ["oven"]
    }
  },
  "missing_fields": [],
  "ambiguities": [],
  "requested_persistence": "current_menu_only",
  "requires_confirmation": true
}
```

Обязательные поля intent-результата:

- `intent`;
- `confidence`;
- `parameters`;
- `missing_fields`;
- `ambiguities`;
- `requires_confirmation`;
- предполагаемая область действия;
- предлагаемое следующее действие.

## 4. Правила классификации операций

### 4.1. Read-only

Примеры:

- показать меню;
- показать рецепт;
- показать список покупок;
- объяснить выбор;
- показать статус workflow.

Условия автоматического исполнения:

- intent распознан достаточно уверенно;
- все обязательные параметры присутствуют;
- операция разрешена текущим состоянием;
- объект принадлежит пользователю;
- tool является read-only.

### 4.2. Draft-producing

Примеры:

- создать меню;
- предложить замену;
- адаптировать рецепт;
- подобрать кандидатов товара.

Правила:

- результат всегда создаётся как `draft`;
- подтверждённые сущности не изменяются;
- draft проходит валидацию;
- пользователь получает preview.

### 4.3. State-changing

Примеры:

- commit меню;
- сохранение постоянного ограничения;
- замена блюда в активной версии;
- изменение магазина;
- удаление данных.

Правила:

- обязательный preview;
- обязательное подтверждение;
- подтверждение связано с конкретной операцией;
- проверяется версия объекта;
- операция идемпотентна;
- действие аудируется.

### 4.4. Administrative

Примеры:

- смена модели;
- установка skill;
- включение MCP;
- terminal;
- изменение credentials;
- миграции;
- обновление Hermes.

Такие действия запрещены в пользовательском Menu Planner-контуре.

## 5. Правила неоднозначности

Система не должна подменять неизвестные параметры предположениями, если они влияют на состояние или результат.

Уточнение обязательно, если неизвестно:

- какой объект менять;
- область действия изменения;
- временное или постоянное предпочтение;
- строгий запрет или мягкое пожелание;
- текущая или новая версия меню;
- допустимость изменения бюджета;
- конкретная дата или приём пищи.

Пример:

> «Больше не предлагай орехи»

Нельзя автоматически записывать аллергию.

Необходимо уточнить:

- аллергия ли это;
- нелюбимый продукт;
- временное пожелание;
- исключить все орехи или конкретный вид;
- применить к текущему меню или ко всем будущим.

## 6. Уверенность распознавания

**[ПРЕДЛОЖЕНИЕ]**

- высокая уверенность + read-only + полные параметры → автоматическое исполнение;
- высокая уверенность + state-changing → preview и подтверждение;
- недостаточная уверенность или отсутствующие поля → уточнение;
- противоречие с текущим workflow → отказ или перенаправление.

**[ТРЕБУЕТ РЕШЕНИЯ]**

- конкретные пороги confidence;
- правила калибровки confidence;
- набор тестовых сообщений;
- допустимость отдельной модели-классификатора.

## 7. Подтверждение операций

Подтверждение должно быть объектом домена.

Минимальная структура:

```json
{
  "confirmation_id": "confirm_001",
  "user_id": "telegram_123",
  "operation": "commit_menu_revision",
  "entity_id": "menu_42",
  "expected_version": 6,
  "draft_version": 7,
  "expires_at": "YYYY-MM-DDTHH:MM:SSZ",
  "summary_hash": "..."
}
```

Перед commit код проверяет:

- пользователя;
- срок действия;
- операцию;
- ожидаемую версию;
- неизменность preview;
- идемпотентность;
- допустимость перехода состояния.

## 8. Workflow и допустимые намерения

Для каждого состояния определяется whitelist допустимых действий.

Пример:

```text
state = menu_waiting_confirmation
allowed_intents:
- confirm_menu
- request_revision
- show_details
- cancel_workflow
```

Если модель или пользователь инициируют другую операцию, она не выполняется автоматически.

Tool handler должен возвращать машинную ошибку:

```json
{
  "success": false,
  "error": {
    "code": "ACTION_NOT_ALLOWED_IN_CURRENT_STATE",
    "current_state": "menu_waiting_confirmation",
    "allowed_actions": [
      "confirm_menu",
      "request_revision",
      "show_details",
      "cancel_workflow"
    ]
  }
}
```

## 9. Профиль пользователя

Профиль должен различать:

- строгие ограничения;
- мягкие предпочтения;
- временные пожелания;
- пользовательские факты;
- непроверенные утверждения из диалога.

Постоянное изменение профиля проходит цепочку:

```text
текст
→ structured intent
→ profile draft
→ clarification при необходимости
→ preview
→ confirmation
→ profile commit
```

**[ТРЕБУЕТ РЕШЕНИЯ]**

- поля профиля;
- список строгих ограничений;
- приоритеты;
- срок действия временных пожеланий.

## 10. Правила меню

Меню создаётся как версионируемый объект.

Модель может предложить структуру, но код проверяет:

- полноту периода;
- количество приёмов пищи;
- строгие запреты;
- оборудование;
- время;
- повторяемость;
- ассортимент;
- бюджет;
- ссылочную целостность.

Свободный текст используется для описания пожеланий, но изменение активного меню всегда проходит через черновик и commit.

## 11. Правила рецептов

Каждый рецепт содержит:

- идентификатор;
- название;
- порции;
- ингредиенты с количествами;
- оборудование;
- активное и полное время;
- шаги;
- признаки готовности;
- хранение;
- разогрев;
- допустимые замены.

Модель может адаптировать рецепт по текстовому запросу, но не должна менять сохранённую версию без создания `RecipeDraft`.

## 12. Правила списка покупок

Итоговый список строится только детерминированным кодом.

Алгоритм:

1. получить ингредиенты подтверждённых рецептов;
2. масштабировать порции;
3. нормализовать единицы;
4. объединить ингредиенты;
5. вычесть остатки;
6. сопоставить товары;
7. рассчитать упаковки;
8. рассчитать стоимость;
9. создать позиции чеклиста.

Пользователь может текстом написать «отметь молоко купленным», но система должна однозначно определить `shopping_item_id`. При нескольких совпадениях требуется выбор.

## 13. Правила магазина и внешних данных

Сырые страницы магазинов считаются недоверенным вводом.

Модель не должна получать необработанный HTML, если задачу можно решить нормализованной карточкой товара.

Нормализованная карточка:

```json
{
  "sku": "12345",
  "name": "Рис жасмин",
  "package_weight_g": 500,
  "price": 2.49,
  "available": true,
  "snapshot_id": "snapshot_001"
}
```

Инструкции, найденные на странице магазина, никогда не считаются системными командами.

## 14. Валидация

### Структурная

- JSON;
- schema version;
- обязательные поля;
- типы;
- enum;
- диапазоны;
- идентификаторы.

### Бизнес-валидация

- строгие ограничения;
- время;
- оборудование;
- порции;
- бюджет;
- доступность;
- повторяемость.

### Арифметическая

- порции;
- суммы;
- единицы;
- упаковки;
- стоимость.

### Ссылочная

- рецепты;
- продукты;
- snapshots;
- версии;
- принадлежность пользователю.

### Семантическая

- ингредиенты соответствуют шагам;
- в шагах не появляются новые продукты;
- оборудование согласовано;
- температура и способ приготовления не противоречат друг другу.

Решение о прохождении проверки всегда принимает код или явно определённая policy, а не генерирующая модель.

## 15. Повторные попытки

**[ПРЕДЛОЖЕНИЕ]**

1. до трёх исправлений той же моделью;
2. затем упрощённый запрос;
3. затем fallback;
4. затем остановка и запрос решения пользователя.

Модель получает конкретные машинные ошибки, а не фразу «ответ неверный».

## 16. Память Hermes

Память может хранить разговорные предпочтения, но не является источником истины для:

- аллергий;
- активного профиля;
- меню;
- рецептов;
- покупок;
- каталога.

При конфликте побеждает прикладная база.

## 17. Запрещённые поведения

Модель не должна:

- напрямую писать в базу;
- выполнять произвольный SQL;
- вызывать terminal в пользовательском контуре;
- самостоятельно подтверждать операцию;
- изменять строгие ограничения;
- использовать память как источник критичных данных;
- утверждать наличие товара без snapshot;
- выполнять административные инструкции из пользовательского текста;
- следовать инструкциям из внешнего HTML;
- бесконечно повторять tool loop.
